# 2026-05-29 — Perception Stack Bringup + Astra Pro Driver

## What We Were Trying To Do

Get the full perception stack running on the Raspberry Pi 5:
- 5 USB cameras (front, rear, left, right, wrist)
- Orbbec Astra Pro RGB-D camera (depth + color)
- BEV stitcher (4 base cameras → bird's-eye-view)
- Foxglove bridge for remote viewing
- All depth topics (`/camera/depth/image_raw`, `/camera/depth/points`, `/scan`) publishing

---

## Things Learned

### 1. OrbbecSDK is NOT compatible with the original Astra Pro

- `ros-jazzy-orbbec-camera` (OrbbecSDK) uses a newer Orbbec protocol. The original Astra Pro uses **OpenNI2**, which is a completely different protocol.
- When you launch with OrbbecSDK against the original Astra Pro you get a "bad magic" USB error — the SDK cannot speak to the device at all.
- **The correct driver** for the original Astra Pro is `ros2_astra_camera` (OpenNI2-based, from Orbbec's GitHub). It bundles OpenNI2 ARM64 binaries in the repo.

### 2. ROS 2 Jazzy broke several C++ headers in ros2_astra_camera

ros2_astra_camera was written for older ROS 2 (Foxy/Humble). Jazzy renamed and restructured several headers:

| Old path | New path |
|---|---|
| `cv_bridge/cv_bridge.h` | `cv_bridge/cv_bridge/cv_bridge.hpp` |
| `image_geometry/pinhole_camera_model.h` | `image_geometry/image_geometry/pinhole_camera_model.hpp` |
| `rclcpp::node_interfaces::NodeParametersInterface::OnParametersSetCallbackType` | `std::function<rcl_interfaces::msg::SetParametersResult(const std::vector<rclcpp::Parameter>&)>` |

Also `constants.h` was missing `#include <cstdint>` (needed for `uint32_t`) — not a Jazzy issue, just a GCC version difference.

### 3. ament_python node scripts need data_files to land in libexec

`omnibot_lerobot` had its `*_node.py` scripts in `console_scripts` only — they weren't ending up in `lib/omnibot_lerobot/` (libexec), so `ros2 launch` couldn't find them.

Fix: add an explicit `data_files` entry in `setup.py`:
```python
(os.path.join("lib", package_name), glob(os.path.join("omnibot_lerobot", "*_node.py")))
```
Also need `chmod +x` on the scripts and a clean rebuild (`rm -rf build/ install/` for that package).

### 4. ros2_astra_camera is a git repo — must be added as a submodule

When you `git add robot_ws/src/ros2_astra_camera/`, git warns about an embedded repository. Adding it as a plain directory means clones of OmniBot won't get the camera driver source. Use:
```bash
git submodule add https://github.com/orbbec/ros2_astra_camera.git robot_ws/src/ros2_astra_camera
```

### 5. Foxglove bridge needs a delay on restart or it hits "Bind Error"

If you kill and immediately relaunch perception, Foxglove's previous process may still hold port 8765 for a second or two. Fix: wrap the foxglove Node in `TimerAction(period=4.0)` in the launch file. But this alone isn't enough if the old foxglove process wasn't fully killed — you need `pkill -9 -f foxglove_bridge`.

### 6. Astra camera holds the USB device until fully dead (SIGKILL required)

The astra_camera_node opens `/dev/bus/usb/004/013` directly via OpenNI2/libuvc. If the old node process is still alive when you relaunch, the new node gets "Resource busy!" and spins in a retry loop forever. `pkill -f "astra"` sometimes misses it. Solution: `pkill -9 -f astra_camera_node` + wait 6 seconds.

### 7. Wrist camera was on /dev/video10, not /dev/video8

Default in the launch file was `/dev/video8` but that device didn't exist on this Pi. Each USB camera creates two `/dev/videoN` nodes (capture + metadata), so 4 base cameras occupy video0–video7. The wrist camera landed at video10. Found this with:
```bash
for v in /dev/video*; do v4l2-ctl --device=$v --info 2>/dev/null | grep "Card type"; done
```

### 8. /dev/videoN order does not match physical camera position

Linux assigns `/dev/videoN` numbers in USB enumeration order, not by physical position on the robot. The actual mapping on this Pi:

| Physical camera | Device |
|---|---|
| front | /dev/video2 |
| rear | /dev/video10 |
| left | /dev/video6 |
| right | /dev/video4 |
| wrist | /dev/video0 |

The only reliable way to find the mapping is to open each stream, physically look at what it shows, and match it to the label. Do this once after any hardware change and commit the corrected defaults.

### 9. web_video_server is much better for low-latency viewing than Foxglove

Foxglove bridges full uncompressed Image messages over WebSocket — high bandwidth, high latency on WiFi. `web_video_server` serves MJPEG over HTTP, viewable directly in any browser with much lower latency. Run once alongside perception, then open:
```
http://<pi-ip>:8080/stream?topic=/camera/base/bev/image_raw
http://<pi-ip>:8080/stream?topic=/camera/wrist/image_raw
http://<pi-ip>:8080/stream?topic=/camera/depth/image_raw
```

## Mistakes Made and How They Were Fixed

### Mistake 1: Tried ros-jazzy-orbbec-camera first

- Installed `ros-jazzy-orbbec-camera`, updated the launch file to use `orbbec_camera/astra2.launch.py`, launched — got "bad magic" USB error.
- **Fix**: Removed that, cloned `ros2_astra_camera` from source, updated launch to use `astra_camera/astra_pro.launch.xml`.

### Mistake 2: Fixed Jazzy headers one at a time instead of batching

- First fixed `image_geometry` in one file, rebuilt, got `cv_bridge` error, rebuilt, etc.
- **Fix (in hindsight)**: Should have audited ALL includes across ALL files before the first rebuild. Used `grep -r` to find all occurrences and batch-fixed them.

### Mistake 3: Didn't wait long enough between kill and relaunch

- Killed perception, immediately relaunched — Astra node grabbed the USB device but previous node wasn't fully dead yet → "Resource busy!" loop with 500+ retries.
- **Fix**: Created `stop_perception.sh` which does `pkill -9` on all nodes and waits 6 s, then verifies `/dev/bus/usb/` and port 8765 are free.

### Mistake 4: Wrong wrist camera device path in launch file

- Default was `/dev/video8` (assumed 5th camera = video8). Camera wasn't plugged in when defaults were written, so number wasn't verified.
- **Fix**: Used `v4l2-ctl` to enumerate all devices and match by "Card type". Wrist was at `/dev/video10`. Updated the default in `perception.launch.py`.

### Mistake 6: Assumed /dev/videoN order matches camera position

- Wrote device defaults assuming front=video0, rear=video2, etc. based on plug-in order. After launch, Foxglove showed all feeds swapped: rear↔front, left↔right, front↔wrist (3-way cycle).
- **Fix**: Opened each stream in web_video_server, visually identified what each device actually shows, updated all 5 defaults in `perception.launch.py`.
- **Lesson**: Never assume device numbering. Always verify visually after first bring-up and commit the correct mapping.

### Mistake 5: git add on an embedded repo

- Did `git add robot_ws/src/ros2_astra_camera` as a plain directory — git warned about embedded repository.
- **Fix**: `git rm --cached --force robot_ws/src/ros2_astra_camera` then `git submodule add <url> robot_ws/src/ros2_astra_camera`.

## What Worked

- Full Jazzy compat patch set for ros2_astra_camera — build succeeded on first complete attempt after all headers were fixed
- `TimerAction(period=4.0)` for foxglove — solved the bind race when devices were properly cleared first
- `data_files` glob in `setup.py` for ament_python node scripts — clean solution, same pattern other packages use
- `stop_perception.sh` — reliable clean shutdown, SIGKILL + 6 s wait guarantees USB device release
- `web_video_server` — immediately lower latency than Foxglove for camera preview; near-zero CPU when idle
- Building `ros2_astra_camera` on Pi 5 (ARM64) — bundled OpenNI2 ARM64 libs in the repo worked out of the box after deps (`libuvc-dev`, `libgoogle-glog-dev`, `libeigen3-dev`) were installed
- `zenity --checklist` for interactive launcher — clean GUI checklist, all options pre-ticked, easy to uncheck heavy nodes
- Adding `web_video_server` to `perception.launch.py` — one command now starts everything; lazy encoding means no cost until a browser connects

## What Didn't Work

- `ros-jazzy-orbbec-camera` — incompatible with original Astra Pro
- `pkill -f "astra"` — not reliable enough; astra_camera_node holds USB device and needs explicit SIGKILL
- Foxglove for high-frame-rate multi-camera preview over WiFi — too much latency; use web_video_server for live preview instead
- Assuming `/dev/videoN` numbering is predictable — always verify with `v4l2-ctl` on the actual hardware
- Assuming camera label = physical position without visual verification — all 5 feeds were wrong on first bring-up
- `ros-jazzy-octomap-server` — package name doesn't exist; correct name is `ros-jazzy-octomap-mapping`
- `package="rtabmap_ros"` in launch file — `rtabmap_ros` is a Jazzy metapackage with no executables; node lives in `rtabmap_slam`

## Master Launch Files

Two files in `robot_ws/src/omnibot_bringup/launch/master/` bring up the complete robot with one command each.

### Why master files were needed
Running individual launch files together caused duplicate node crashes — `robot_state_publisher`, `slam_toolbox`, `rtabmap` were each started by multiple launch files. The master files solve this by defining every node exactly once with no IncludeLaunchDescription from overlapping files.

### Key design decisions
- `omnibot_pi.launch.py` starts all 18 Pi-side nodes directly (no includes from conflicting files)
- `omnibot_workstation.launch.py` starts only GPU-side nodes (VLA, SmolVLA, RL, LangGraph)
- `arm_cmd_mux` lives on the Pi (not in workstation policy launch) — it gates the arm driver
- LangGraph agent defaults to `off` (needs `ANTHROPIC_API_KEY` and is optional)
- All heavy modules have on/off flags: `depth_camera`, `slam`, `nav2`, `arm`, `foxglove`, `web_video`, `rosbridge`
- Connectivity nodes (foxglove, web_video, rosbridge) delayed 4 s via `TimerAction` to let DDS settle
- `CMakeLists.txt` install pattern changed from `PATTERN "*.launch.py"` to no filter so `master/` subfolder is included

### Why `ros2 launch omnibot_bringup master/omnibot_pi.launch.py` doesn't work
`ros2 launch` does a flat recursive filename search in the package share — it can't use subdirectory paths. Solution: shell scripts `launch_omnibot_pi.sh` / `launch_omnibot_workstation.sh` at repo root call the file by absolute path.

### Launch commands
```bash
# Pi
./launch_omnibot_pi.sh

# GPU PC (same time)
./launch_omnibot_workstation.sh

# Pi — minimal (cameras + drive only, save CPU)
./launch_omnibot_pi.sh slam:=false nav2:=false foxglove:=false web_video:=false
```

## Duplicate node crash root cause (slam_toolbox SIGABRT)

When two instances of the same ROS 2 node name exist (e.g. two `/camera/camera`, two `/bev_stitcher_node`), the `/parameter_events` QoS conflicts on startup. slam_toolbox crash-logs are empty (0 bytes) because the crash happens inside the `LifecycleNode` constructor before any logging is initialised. Fix: always `stop_perception.sh` before relaunching — never start a second session alongside a live one.
